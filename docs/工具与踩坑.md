## 2026-07-31 - LinX 广播模式安装和 UI 自动化

- **添加页选择项缺失**：选择 `MicroTech LinX` 后进入的添加页此前只有搜索按钮，没有 `直接连接 / 广播数据` 选择；修复后选择项位于搜索按钮上方，默认是 `直接连接`。
- **广播模式边界**：广播模式只扫描 Aidex 广播并解析最新血糖，不主动连接设备，不读取历史，不监听其它 App 的蓝牙连接。
- **广播日志判断顺序**：先看 `stage=broadcast event=started` 判断扫描是否开始；再看 `found` 判断是否收到 BLE 广播；再看 `parsed` 判断 Aidex 厂商数据是否解析成功；最后看 `accepted` 或 `rejected reason=...` 判断是否写入 Loop。没有 `found` 且出现 `timeout/stopped`，优先判断为没有扫到广播或系统扫描受限。
- **广播日志字段**：`parsed` 和 `accepted` 会记录 identifier、name、RSSI、serial、sample、value、trend、status、records 和完整 rawHex；`parseError` 会记录 identifier、name、RSSI、错误原因和原始 advertisement。
- **广播出现 `value=255 quality=255`**：真机包 `59000000010300FFFFFFFFFFFFFFFFFFFFFFED99C18B` 的字段位置没有解析错，设备实际广播的是 `timeOffset=0` 和 `FF FF FF` 占位记录。`timeOffset` 小于 7 表示探头未开始或仍在预热，`0xFF` 也不是有效血糖；两种情况都必须拒绝并继续扫描，不能把 `255 mg/dL` 写入 Loop。
- **有效最新值后仍有 `FF`**：广播最多携带三条记录；最新一条有效而后续历史位置为 `FF FF FF` 时，只保留最新有效值并停止读取后续占位位置，不能因此丢弃整包。
- **升级前已保存 `255`**：旧版可能已经把 `sample=0`、`255 mg/dL` 保存到广播状态。新版读取状态时会清除预热样本和 `255` 占位血糖，但保留已绑定传感器，避免错误值继续显示。
- **`BWCGM` 设备解析成功但不入库**：真机发现 `BWCGM-22222BGWQD` 的有效广播 `590042540000EB98804C9B804CA0804A000072034DFD`，可解析为 sample `21570`、血糖 `152`；此前设备名识别只支持 `LinX` 和 `AiDEX`，导致 serial 为空。广播与直连设备名识别现同时支持 `BWCGM-序列号`。
- **无过滤扫描日志暴增**：广播 fallback 使用无 service 过滤扫描时，iOS 会回调附近所有 BLE 设备。必须先按厂商标识 `59 00` 过滤，再记录 `found` 和解析；否则几十秒内会产生大量无关 LinX 日志。
- **日志队列偶发空结果**：`DispatchSpecificKey` 只保存 `Bool` 时，释放后的 key 地址可能被新队列复用，导致新队列把旧队列误认为自己，`flush` 提前返回。每个日志队列必须保存并比较独立 UUID，避免广播诊断日志未写完就被读取。
- **避免误判**：广播模式发现设备时只应出现 `stage=broadcast event=found`，不应同时出现 `stage=scan event=found`；如果两者混在同一次广播发现里，会误导为直连扫描路径。
- **广播搜不到但直连能搜到**：直连可以通过已连接外设、保存的 identifier 或 service UUID 找到设备；广播实时血糖包可能只带厂商数据 `0x0059`，不带 Aidex service UUID。此时 iOS 的 service UUID 过滤会在回调前丢掉广播。处理方式是广播模式先用 service UUID 过滤扫描，超时后记录 `stage=broadcast event=fallback reason=filteredTimeout`，再切到 `withServices: nil` 扫描；后续仍只接受名称、identifier 和厂商数据匹配的 Aidex/LinX 广播。
- **Debug 真机安装注意**：`CODE_SIGNING_ALLOWED=NO` 的 generic 构建产物不能直接安装到真机，会报 `No code signature found`；真机安装必须使用开发签名构建，并显式使用当前团队 `DEVELOPMENT_TEAM=HHZN32E89C`。
- **真机 UI 自动化注意**：本次执行 `LoopUITests/LoopCGMSetupUITests/testMicroTechLinXSetupOpensFromSettings` 时，XCTest 失败点是 `Timed out while enabling automation mode`，未进入 LinX 页面断言；这类结果只能说明手机自动化模式未启用成功，不能作为添加页不存在选择项的证据。
- **启动排查**：Debug 包安装后可用 `xcrun devicectl device process launch --device E30C92D5-FE26-5AE1-B5FB-C787E4401F4F --terminate-existing com.libre.loopkit3.Loop` 启动；同时检查 `~/Library/Logs/CrashReporter/MobileDevice` 下最近的 `Loop*.ips` 判断是否有新崩溃。

## 2026-07-30 - LinX 首次添加完整日志与排查

- **首次添加失败未进入 DeviceLog.json 的原因**：首次添加使用的临时 manager 尚未成为正式 CGM manager，因此没有正式的 `CGMManagerDelegate`，失败日志不会经过正式 manager 的日志入口。
- **处理**：LinX onboarding 增加独立日志处理器，并在扫描开始前接入 `PersistentDeviceLog`。该处理器只负责记录添加期间的日志，不会预先安装一个添加失败的 manager；首次扫描失败也能随 Loop Report 导出。
- **停止位置判断**：按同一设备日志中最后出现的 `stage` 和 `event` 判断流程停点。`scan` 记录扫描开始、发现、接受或拒绝、停止和超时；`connect` 记录连接进度与结果；`restore` 记录系统恢复的设备；`bluetooth` 记录蓝牙状态变化；`gatt` 记录服务、特征、通知、读写操作及超时；`handshake` 记录密钥材料、challenge 和会话建立；`packet` 记录命令发送、密文接收、解密及解析结果。排查时从最后一个成功事件继续查看紧邻的失败或超时事件。
- **Loop Report 内容**：LinX 日志持续写入完整设备 identifier、base key、pairing key、session key、IV、challenge、已发送命令、加密包和解密包；这些值不脱敏、不截断，以便还原首次添加和后续通信问题。
- **安全要求**：Loop Report 含设备密钥和完整通信数据，只能交给可信分析人员，不得上传到公开 issue、公开网盘、论坛或其他公开位置。
- **全量验证**：`MicroTechCGM` 的 `Shared` scheme 在 `iPhone 17` Simulator 上通过 165 个测试，0 失败；`testSerialLogQueueDoesNotLetSlowHandlerBlockReadCompletion` 又独立运行 3 次，每次均为 1 个测试、0 失败。`LoopWorkspace` 使用 `generic/platform=iOS` 且 `CODE_SIGNING_ALLOWED=NO` 构建成功。
- **DeviceLog.json 导出验证**：直接用 `LoopWorkspace` scheme 运行指定测试时，被仓库现有的 `OmniBLETests/Driver/Comm/message/MessagePacketTests.swift:52` 编译错误阻断，原因是 `RawSpan` 没有 `toHexString`。改用 `LoopTests` scheme，并明确指定 Simulator id 与 `MAIN_APP_BUNDLE_IDENTIFIER=com.libre.loopkit3.Loop` 后，指定测试 1 个通过、0 失败；导出结果中确认存在 `stage=scan event=failed reason=timeout`。
- **LoopTests 运行注意**：必须明确指定 Simulator id 和 `MAIN_APP_BUNDLE_IDENTIFIER`，否则会受到仓库现有 Watch companion bundle ID 安装问题影响。
- **Git 代理注意**：全局 Git 代理 `127.0.0.1:1081` 不可用时，只对当前命令临时覆盖为 `127.0.0.1:1082`，不要修改全局配置。本次验证网络正常，未使用该临时覆盖。

## 2026-06-29 - TestFlight Watch 安装失败

- **现象**：TestFlight 中 `Loop` 主 App 可见，但 Apple Watch 安装提示“无法将 Loop 安装在 Apple Watch 上。重试。”；用户手表为 Apple Watch Series 8，watchOS `11.6.2 (22U95)`。
- **原因**：成功上传的 TestFlight IPA 内已包含 `WatchApp.app` 和 `WatchApp Extension.appex`，但 Watch 相关 `arm64` slice 的 Mach-O 最低系统被标为 `watchOS 26.0`；`WatchApp`、`WatchApp Extension`、`LoopCore.framework`、`LoopKit.framework` 都受影响。Apple 上传又要求 watchOS 包保留 `arm64`，不能简单回退为只含 `arm64_32`。
- **处理**：`fastlane build_loop` 在 `gym` 导出后执行 `Scripts/patch_watchos_testflight_compatibility.sh`，保留 IPA 顶层 `WatchKitSupport2/`，跳过 `WatchApp.app` 主壳，修正 `WatchApp Extension.appex` 和其依赖 framework 的 `arm64` slice 最低系统为 `watchOS 9.0`，随后重新签名受影响内容和 `Loop.app`，再用 `Scripts/verify_watchos_testflight_compatibility.sh` 验证。
- **验证**：旧 TestFlight IPA 用验证脚本检查会失败，失败点为 Watch `arm64` slice 的 `minos=26.0 > 11.6`；当前修正后的 `Loop 3.9.1 (64)` 已完成 App Store Connect 处理；验证脚本通过，`WatchKitSupport2/WK` 与 `WatchApp.app/_WatchKitStub/WK` 的 SHA256 完全一致，`WatchApp Extension`、`LoopCore.framework`、`LoopKit.framework` 的 `arm64` slice 已显示 `minos 9.0`。
- **Actions 注意**：fastlane 的 `sh` 调用本仓库脚本时不要使用相对路径；应使用 `GITHUB_WORKSPACE` 计算仓库绝对路径，并通过 `bash` 执行脚本。`Scripts/...` 和 `./Scripts/...` 都可能因为 fastlane 当前目录变化而报 `No such file or directory`。
- **App Store Connect 处理注意**：错误 `90589 Invalid WatchKit Support` 和 `90484 WatchKitSupport2 folder is missing` 说明 IPA 顶层缺少 `WatchKitSupport2/`。修正脚本重新压包时必须保留 Xcode 导出的所有顶层目录，不能只压 `Payload/`。发布流程也必须等待 App Store Connect 处理结果，不能只把上传完成当成成功。
- **WK 匹配注意**：错误 `90487 Invalid WatchKit Support` 说明 `WatchKitSupport2/WK` 和 Watch app 内的 `_WatchKitStub/WK` 校验不匹配。修正脚本不能处理 Watch app 壳本身，只能处理 `WatchApp Extension.appex` 和其依赖 framework；验证脚本必须检查两份 `WK` 的 SHA256 完全一致。
- **避免**：以后升级 Xcode 或 watchOS SDK 后，发布前必须检查 IPA 内 Watch slice 的 `LC_BUILD_VERSION`，不能只看 `Info.plist` 的 `MinimumOSVersion`。
